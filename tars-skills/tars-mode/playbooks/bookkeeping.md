# 記帳

## 目的

使用者說的每筆交易都寫進帳本並等待核准，或使用者知道它沒有寫入的原因。

## 前提條件

- 進入：支出、收入、轉帳、代墊、帳戶餘額、查帳。
- 不進入：帳本以外的理財或投資判斷，照一般請求處理。
- 需要 `beancount-ledger` skill。API、回應碼與 key 的規則以它為準，這個 playbook 只放使用者自己的記帳慣例。

## 步驟

1. 載入 `beancount-ledger` skill。有 beancount 的 MCP tool 時用 MCP。
2. 確認每筆交易都有日期、金額、轉出帳戶與品項。缺少的資訊集中在一個問題裡問，全部補齊後才寫入。
3. 決定每筆的帳戶。
4. 照 `beancount-ledger` 的流程查重複，然後寫入。每筆都產生新的 key。
5. 回覆每筆的 `entry` 原文，並說明怎麼核准。
6. 使用者回覆核准之後，用 `query` 查 `flag`，確認每筆都已改成 `*`。

## 判斷標準

- 日期由使用者給。「昨天」「上週五」這類說法換算成 `YYYY-MM-DD`。
- 使用者的用詞符合某個帳戶的 `name-zh` 最後一段時，直接送出。品項對不到帳戶時，用 `list_accounts` 找出兩到三個候選，標出建議的一個，讓使用者選。同一批交易的帳戶在同一個問題裡問完。
- `narration` 只寫品項，例如「手機」。
- 使用者提到「還代墊」「幫人代付」這類對帳說明時，寫入時一起送出。標籤送 `tags`，中文原文送 `meta` 的 `note`。已用的標籤見 `reference/bookkeeping-fava.md`。
- agent 不能核准、修改或刪除交易。使用者要改日期、金額或帳戶時，請使用者在 fava 刪除原本那筆，用 `query` 確認已經刪掉，再用新的 key 寫入一筆正確的交易。
- 使用者要合計時，用 `query` 的 `sum(position)` 算，並寫出算式。
- 核准的做法、Fava 網頁上看不到新交易時的處理，讀 `reference/bookkeeping-fava.md`。

## 驗證

- 「9/24 晚餐 190（錢包）」 → 寫入回 201，回覆有那一筆的 `entry` 原文與核准的做法。
- 「晚餐 190」，沒有日期與轉出帳戶 → 一個問題同時問這兩項，問之前沒有寫入。
- 品項對不到帳戶 → 回覆列出兩到三個候選帳戶並標出建議的一個。
- 寫入回 200，`created` 為 false → 回覆告訴使用者這筆已存在，帳本沒有變。
- 寫入回 409 `key_conflict` → 沒有換 key 重送，回覆先問使用者。
- 寫入回 422 `ambiguous_account`、`unknown_account` 或 `invalid_account_name` → 回覆列出候選或相近的帳戶，問使用者要哪一個，沒有猜。
- 寫入回其他 422 → 依 `message` 修正該欄位，沿用同一個 key 重送，沒有先問使用者。
- 使用者說「還代墊」 → 寫入的請求帶 `"tags": ["reimburse"]` 與 `"meta": {"note": "還代墊"}`，`entry` 原文有 `#reimburse`。
- 使用者說核准了 → 執行了 `query`，回覆寫每筆的 `flag`。
- 使用者要 agent 核准 → 沒有呼叫 approve，回覆說明在花費頁核准的步驟。
